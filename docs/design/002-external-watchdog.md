---

## 1. 目标

让每天三期（技术日报、财经早报、财经晚报）**在计划时刻之后十几分钟内一定出现**，
不再依赖 GitHub Actions 的计划任务。

### 非目标

- 不做历史补采（过去某天缺了就缺了，不自动回填）
- 不替代站点部署（发布仍由 Actions 完成）
- 不做告警/通知（后续可加）
- 不改核心管道的任何生成逻辑

### 反目标（做了就是失败）

- 同一个时段被反复触发、反复重跑
- 令牌以明文出现在仓库或日志里
- 服务器宕机期间把当天三期全错过（必须能自愈）

---

## 2. 现状与问题

GitHub 计划任务的延迟在 10 月下旬约 2.3 小时，11 月中旬已恶化到 **8 小时以上**：

| 日期 | 任务 | 计划 | 实际 | 延迟 |
|---|---|---|---|---|
| 11-18 | 财经晚报（主跑） | 17:30 | 次日 02:16 | +8h46m |
| 11-18 | 财经晚报（补跑） | 21:47 | 次日 05:36 | +7h49m |
| 11-13 | 技术日报（主跑） | 07:17 | 11:25 | +4h8m |

由此产生两个后果：

1. **补跑失效**。主跑和补跑被同样延迟，到达时间只差几分钟，等于少了一层保险。
2. **跨午夜生成残缺期**。11-19 晚报在凌晨 05:36 被生成，窗口 `05:30 → 17:30`
   才刚开始 6 分钟，只抓到 10 条，还因幂等保护挡住了当天真正的运行。

第 2 点已经用「未来窗口守卫」止血（`end > now` 即拒绝），但**当天缺一期**的问题仍在。

---

## 3. 方案

### 3.1 选型

| 方案 | 描述 | 结论 |
|---|---|---|
| A 定点触发 | 服务器在 05:30/07:00/17:30 各打一枪 | 否定：只负责发出去，不负责发成功；失败、排队、服务器重启都会丢期 |
| **B 对账巡检** | 每 10 分钟检查产物是否存在，缺了才触发 | **采用**：自愈、不赌“那一分钟”、失败会自动重试 |
| C 定点 + 巡检 | 两者都做 | 否定：逻辑翻倍，收益只有十几分钟 |

### 3.2 巡检逻辑

```
每 10 分钟（服务器本地定时器）：
  now = 当前北京时间
  git pull 拉取最新配置（拿 publish_at / content_dir）

  for 每个栏目时段（tech / finance-morning / finance-evening）:
      end = 今天 + publish_at
      目标文件 = content_dir/<profile>/<Y>/<M>/<DD>[-slot].md

      若 now < end + 15 分钟            → 还不到时候，跳过
      若 now > end + 6 小时             → 已过期，当天放弃（打日志）
      若 目标文件已存在                  → 已完成，跳过
      若 30 分钟内已经触发过同一时段      → 冷却中，跳过
      否则 → dispatch，并记录触发时间
```

**为什么是 15 分钟宽限**：给 Actions 自身排队留时间，避免和已经排上的运行撞车。

**为什么要有 6 小时上限**：过期后窗口内容已经不对（比如早上 11 点才去补 05:30 的期），
且会与「未来窗口守卫」形成无效循环——守卫拒绝、巡检又重试，每 30 分钟空转一次。

### 3.3 关键实现决定

| 项 | 决定 | 理由 |
|---|---|---|
| 是否存在 | 用 **GitHub Contents API**（带令牌），不用 raw.githubusercontent.com | raw 有 CDN 缓存（最长 5 分钟），会误判“文件不存在”而重复触发 |
| dispatch 参数 | 显式传 `date`（北京时间当天） | 即使 Actions 排队跨天，生成的仍是正确日期那期 |
| 触发冷却 | 同一时段 30 分钟内只触发一次，记在本地状态文件 | 一次运行要 2–5 分钟，没有冷却会连发好几个 |
| 时区 | 脚本内部强制 `Asia/Shanghai` | 海外机房多半是 UTC，不比依赖系统时区安全 |
| 令牌 | 服务器本机 `/etc/digest-watchdog.env`，`chmod 600` | 不入库、不进日志 |
| 令牌权限 | fine-grained PAT，仅该仓库的 **Actions: write** | 泄露后最坏是能触发构建，不能读写代码 |
| 语言 | Python 3 标准库 | 与项目一致，零依赖 |
| 与 GitHub cron 的关系 | **保留不动** | 第二层保险；幂等保护保证不会重复生成 |

### 3.4 部署形态

脚本入库：`tools/watchdog.py`。
服务器上 `git clone` 一份，由 systemd timer 每 10 分钟执行；systemd 不可用时退回 crontab。

```ini
# /etc/systemd/system/digest-watchdog.timer
[Timer]
OnCalendar=*:0/10
Persistent=true
```

`Persistent=true` 保证服务器宕机后开机补跑一次。

---

## 4. 验收标准

1. 文件存在时运行脚本 → 不发任何 dispatch 请求（日志写明“已完成，跳过”）
2. 手动删掉当天某期 → 运行脚本 → 触发一次，且 30 分钟内再运行不重复触发
3. 未到 `publish_at + 15 分钟` → 不触发
4. 超过 `publish_at + 6 小时` 且缺文件 → 不触发，日志写明“已过期”
5. 服务器时区设为 UTC 时，仍按北京时间判定
6. 令牌缺失或失效 → 非零退出并给出明确错误，不静默通过
7. 日志里不出现令牌

---

## 5. 风险与回滚

| 风险 | 缓解 |
|---|---|
| 令牌泄露 | 只给 `Actions: write`；可随时在 GitHub 后台吊销；服务器文件权限 600 |
| 服务器故障 | GitHub cron 仍在作为第二层；幂等保护防止重复生成 |
| 重复触发导致内容被覆盖 | 幂等保护（AGENTS 第 3 条）挡住；冷却进一步降低概率 |
| 巡检误判“文件不存在” | 用认证 API 而非 CDN；误判最多浪费一次运行，不会破坏内容 |
| 与未来窗口守卫冲突 | 巡检上限 6 小时，守卫下限 5 分钟，两者不重叠 |

**回滚**：停掉 systemd timer 即可，仓库里只是多了一个未被调用的脚本，管道行为零变化。
